# RFC 0009: The CI gate, set up by render

| Field | Value |
|-------|-------|
| Author | @AbuMahir980 |
| Status | Accepted |
| Proposal issue | #103 |

## Summary

`peer-ai check` is the gate that holds work to its record in CI, but today a person has to remember to add it, and the one line the README gives works only in a project with Peer AI in its `package.json`. `render` will set the gate up itself: in a project on GitHub Actions, it writes a workflow of its own that installs Node 24 and runs the exact version of Peer AI the project uses; for any other CI, it prints the step to add. `peer-ai doctor` warns when no CI runs the gate, so the AI tool hears about it at the start of every session (RFC 0007) and adds it, or tells the person.

## Motivation

**The one step still left to memory.** RFC 0007 made the setup checks run themselves: CI fails when the setup breaks, and the AI tool hears about any setup problem in every session. All of that depends on CI running `peer-ai check`, and nothing sets that up. The README says to add `- run: npx peer-ai check` to CI after the project's own checks, and nothing reminds anyone after that.

**It went unnoticed on the first real setup.** On the first project set up from the npm pre-release, the person ran `init`, `assess` and `render`, then asked more than once whether the README's line was something they still had to do; nothing in Peer AI had told them. The line wouldn't have worked there anyway. The project has a Python API, mobile apps and Terraform, and no `package.json` at its root, so the runner had neither Node 24 nor an installed Peer AI for `npx peer-ai` to find. Both projects due to move onto 1.0 next use GitHub Actions, and neither runs the gate.

## Design

### 1. render writes the gate for GitHub Actions

When the project's CI is GitHub Actions (a `.github/workflows/` folder, or `delivery.pipeline` inside it), `render` writes `.github/workflows/peer-ai.yml`:

```yaml
# Generated by peer-ai render from peer-ai.config.json: the gate, peer-ai check.
# Change the config, not this file. Render writes it again while it's as render left it, and leaves
# it alone once someone changes it by hand. Make the job a required check: its name never changes.
# peer-ai sha256: <hash>
name: Peer AI
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  peer-ai-check:
    name: peer-ai check
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@<commit> # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/setup-node@<commit> # v7.0.0
        with:
          node-version: 24
      - run: npx -y peer-ai@1.0.0-next.2 check
```

- **The version is the one `render` runs as,** the same version the MCP server command and the skills setup step name. A version bump changes it, in the same change as the rest.
- **The actions are pinned to a commit,** as in the setup steps `render` already writes. `push` lists the default branch only when the config names one (`repo.defaultBranch`), as the security workflow does.
- **Ownership works as it does for the security workflow** (RFC 0006): a hash in the header records what `render` wrote. While the file is unchanged, `render` keeps it up to date. Once someone changes it by hand, `render` leaves it alone, and `doctor` checks that it still runs `peer-ai check`.
- **No second gate.** When another workflow already runs `peer-ai check`, because someone added it by hand, `render` writes nothing and says why.

### 2. Other CI: the step to add

For any other CI that `init` recognises, such as GitLab CI, Jenkins or Bitbucket Pipelines, `render` can't safely edit the pipeline's file. It prints the step instead, among its manual steps:

> Add a step to your CI that runs with Node 24, after the project's own checks: npx -y peer-ai@1.0.0-next.2 check

### 3. doctor warns when nothing runs the gate

A new check, `gate`. When the project has CI and no CI file runs `peer-ai check`, it warns:

> No CI runs peer-ai check, so nothing holds work to its record. Fix: run npx peer-ai render, which sets it up for GitHub Actions, or add the step it prints to your CI.

It is a warning, not a failure: `check` can't fail CI for a gate that isn't in CI. Through `next_work` (RFC 0007), the AI tool hears about it at the start of every session. A project with no CI yet gets no warning, since `assess` already records CI as a gap for the stage that needs it.

### 4. Turning it off

`delivery.gate`, a new optional key, defaults to `true`. Set to `false`, `render` writes no gate and prints no step, and `doctor` doesn't warn. That suits a project whose CI runs the gate some other way, such as inside a larger build script.

### 5. The documentation

The README and the `check` section say that `render` sets the gate up. They no longer ask anyone to add a line by hand.

## Compatibility

Minor. Projects on GitHub Actions get one new file the next time `render` runs, usually in the same change as a version bump. A project that already runs `peer-ai check` in a workflow of its own gets nothing new. The config schema gains one optional key, `delivery.gate`.

## Drawbacks

- **One more file in the repository,** and one more job on every pull request: Node is downloaded, and a pinned version of Peer AI runs, which takes seconds.
- **A version bump touches the workflow,** as it already touches the AI tools' settings.
- **The job is required only when the person makes it so.** Branch protection is the repository owner's setting, and `render` can't change it. The file's header and the README say to make `peer-ai check` a required check.

## Alternatives

- **Adding a job to the project's own workflow file.** That means editing someone's YAML, with its comments and anchors, and a mistake breaks their CI. A file of Peer AI's own is safe to write, rewrite and delete.
- **Better documentation only.** That's what exists today, and the first real setup missed it.
- **Only the doctor warning.** That still leaves the work to a person or the AI tool each time. For the common case, the workflow can be written once, safely.

## Open questions

- **Should a prototype get the gate?** Proposed: yes. `check` is lenient at the prototype stage, and the gate is already in place for when the project grows.
- **Should `migrate` mention making the job required?** Proposed: yes, as one line in its notes, since it's a setting only the owner can change.
